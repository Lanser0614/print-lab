# Технический дизайн карты доставки для заявок PrintLab

Дата: 2026-05-24
Статус: черновик для ревью

## Цель

При оформлении заявки пользователь должен указать адрес доставки в пределах города Ташкент. Интерфейс должен помочь определить адрес через GPS и карту, но оставить пользователю ручной контроль: он может передвинуть пин на карте или ввести адрес сам.

Админ должен видеть адрес доставки на странице заявки и карту с точкой доставки.

## Что входит в этап

- Добавить обязательный адрес доставки при создании заявки.
- Добавить карту в UI оформления заявки.
- Запрашивать разрешение браузера на GPS через Geolocation API.
- Если GPS разрешен, ставить пин на текущую позицию пользователя.
- Если GPS запрещен или не сработал, показывать карту Ташкента и дать пользователю выбрать точку вручную.
- Разрешить пользователю двигать пин по карте.
- Сохранять адрес, город, широту и долготу в заявке.
- Проверять, что выбранная точка находится внутри разрешенной зоны Ташкента.
- Показывать адрес и карту с пином в админке Filament.

## Что не входит в этап

- Расчет стоимости доставки.
- Доставка за пределы Ташкента.
- Выбор района, филиала, курьера или временного слота.
- Полноценная логистика и трекинг доставки.
- Поддержка нескольких адресов в аккаунте пользователя.

Эти функции можно добавить позже, когда появится понятный процесс доставки.

## UX оформления заявки

В форме заявки после имени и телефона появляется блок "Адрес доставки".

Поведение блока:

- карта открывается с центром на Ташкенте;
- браузер запрашивает разрешение на определение местоположения;
- если пользователь разрешил GPS, карта ставит пин на текущую позицию;
- если координаты находятся внутри Ташкента, пользователь может отправить заявку;
- если координаты вне Ташкента, UI показывает ошибку и просит выбрать адрес внутри города;
- если пользователь запретил GPS, пин остается в центре Ташкента или на дефолтной точке, а пользователь сам двигает его;
- пользователь может вручную перетащить пин в нужную точку;
- после движения пина UI обновляет координаты и, если возможно, текстовый адрес;
- текстовый адрес можно отредактировать вручную.

Обязательные поля перед отправкой:

- имя;
- телефон;
- адрес доставки;
- координаты доставки;
- товар, вариант, количество и дизайн, как сейчас.

Сообщение при точке вне города:

> Доставка доступна только по Ташкенту. Выберите адрес внутри города.

## Карта

Рекомендуемый провайдер: Yandex Maps.

Причины:

- лучше подходит для адресов Ташкента на русском и локальных названий;
- поддерживает интерактивную карту, draggable marker и геокодинг;
- удобнее для админов, которые будут работать с адресами в Узбекистане.

Ключ для Yandex Maps хранится в `.env`, например:

```dotenv
YANDEX_MAPS_API_KEY=
```

Frontend получает ключ через безопасную конфигурацию страницы или Vite env, в зависимости от текущего подхода проекта. Ключ должен быть ограничен по домену в кабинете Yandex.

## Данные

В `order_requests` нужно хранить:

- `customer_city` - город доставки, нормализованное значение `Tashkent`;
- `customer_address` - текстовый адрес доставки;
- `delivery_lat` - широта выбранной точки;
- `delivery_lng` - долгота выбранной точки;
- опционально `delivery_geo_provider` - провайдер геокодинга, например `yandex`;
- опционально `delivery_geo_payload` - короткий JSON с исходными данными геокодинга для отладки.

Минимальный обязательный набор для этапа:

- `customer_city`;
- `customer_address`;
- `delivery_lat`;
- `delivery_lng`.

## Backend validation

`StoreOrderRequestRequest` должен требовать:

- `customer_address`: required, string, max 2000;
- `customer_city`: required, string, accepted value `Tashkent` или локальные варианты, которые нормализуются;
- `delivery_lat`: required, numeric;
- `delivery_lng`: required, numeric.

После базовой валидации backend проверяет, что точка внутри разрешенной зоны Ташкента.

Для первого этапа достаточно polygon/bounds validation без внешнего API:

- хранить polygon Ташкента в backend support-классе или config;
- проверять point-in-polygon для `delivery_lat` / `delivery_lng`;
- возвращать validation error, если точка вне зоны.

Так заявка не сможет пройти только за счет подмены frontend payload.

## Frontend data flow

Текущие формы конструктора отправляют заявку в `order-requests.store`.

Payload нужно расширить:

```json
{
  "customer_name": "Doniyor",
  "customer_phone": "+998901234567",
  "customer_city": "Tashkent",
  "customer_address": "Tashkent, Chilanzar ...",
  "delivery_lat": 41.2995,
  "delivery_lng": 69.2401
}
```

Остальные поля заявки остаются как сейчас: `product_id`, `variant_id`, `quantity`, `designs` или legacy `side/canvas_json/preview_image/print_image`.

## Админка

В Filament resource заявок нужно показать доставку в двух местах.

В таблице заявок:

- колонка "Адрес" после телефона;
- короткий текст с `limit(40)`;
- поиск по адресу.

На странице просмотра/редактирования заявки:

- секция "Доставка";
- город;
- полный адрес;
- координаты;
- интерактивная или embedded карта с пином.

Для карты в админке можно использовать тот же Yandex Maps JS API. Пин в админке не должен менять координаты, если это view-режим. В edit-режиме можно оставить адрес и координаты readonly на первом этапе, чтобы админ не изменил точку случайно.

## Ошибки и fallback

GPS может не работать по нескольким причинам:

- пользователь запретил permission;
- браузер не поддерживает Geolocation API;
- сайт открыт не через HTTPS в production;
- устройство не смогло определить координаты;
- координаты вне Ташкента.

UI должен во всех случаях сохранять рабочий ручной путь:

- карта остается доступной;
- пользователь может перетащить пин;
- адрес можно ввести вручную;
- отправка блокируется только если нет адреса, нет координат или точка вне Ташкента.

Если Yandex Maps JS не загрузился, форма должна показать понятную ошибку и не отправлять заявку без координат.

## Security and privacy

- Запрашивать GPS только в момент оформления заявки, когда пользователь понимает зачем это нужно.
- Не получать геолокацию в фоне.
- Не хранить больше геоданных, чем нужно для доставки.
- Не доверять frontend-проверке города: backend validation обязательна.
- API key карт должен быть ограничен по домену.

## Тестирование

Feature tests:

- заявка создается, если адрес и координаты внутри Ташкента;
- заявка отклоняется без адреса;
- заявка отклоняется без координат;
- заявка отклоняется, если координаты вне Ташкента;
- сохраняются `customer_city`, `customer_address`, `delivery_lat`, `delivery_lng`.

Unit tests:

- point-in-polygon checker принимает координаты внутри Ташкента;
- отклоняет координаты за пределами Ташкента;
- корректно работает на границе polygon.

Frontend/browser checks:

- GPS permission success path;
- GPS denied path;
- draggable pin updates hidden fields;
- ручной адрес сохраняется;
- ошибка вне Ташкента видна до отправки;
- карта не ломает мобильную форму заявки.

Admin checks:

- адрес виден в таблице заявок;
- страница заявки показывает полный адрес;
- карта в админке показывает пин по сохраненным координатам.

## Открытые решения

- Точные границы Ташкента нужно зафиксировать в polygon. На первом этапе можно использовать приближенный polygon, но его нужно хранить явно в коде и покрыть тестами.
- Нужно решить, будет ли reverse geocoding автоматически перезаписывать адрес после движения пина или только предлагать значение пользователю.
- Нужно решить, разрешаем ли админу редактировать координаты в админке на первом этапе. Рекомендация: сначала readonly.
